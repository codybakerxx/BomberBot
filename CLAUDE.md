# BomberBot: notes for Claude

BomberBot is a top-down bomber battle game for the browser, built for phones. The owner directs the project and play-tests every change on a phone. Claude writes the code. Explain what you did in plain words, and lead with what changed for the player.

## Commands

```sh
npm install        # once
npm run check      # type-check, tests, build: run this before calling anything done
npm test           # tests only
npm run build      # writes dist/index.html, the whole game in one file
```

## Where things are

- `src/sim.ts`: all game rules. `src/swipe.ts`: the swipe pad. `src/teach.ts`: Match my thumb maths. `src/bot.ts`: the CPU players.
- `src/input.ts`, `src/render.ts`, `src/audio.ts`: input wiring, drawing, sound. `src/robot.ts`: how the robot is drawn (handed on through `render.ts`).
- `src/main.ts`: loop, title screen, Settings, the menu during a match, the score, layout. `src/lobby.ts`: the lobby. `src/setup.ts`: what the lobby and Settings choose, and saving it. `src/ui.ts`: the menus' controls. `src/title.ts`: the title screen's picture. `src/page.html`: markup and styles.
- Online play (`docs/ONLINE.md`): `src/net.ts` (the messages, input codes, checksums: pure), `src/room.ts` (one room: lobby, host, the match, run on the server; no network or clock of its own), `src/worker.ts` (the Cloudflare server: a Durable Object per room code), `src/online.ts` (the page's connection), `src/predict.ts` (the round on the page: the picture run ahead of the server so your robot moves at once; pure, the time is handed in). `wrangler.jsonc` says what is uploaded; GitHub uploads it on every push to `main`. The game is at https://bomberbot.bomberbot.workers.dev.
- `tests/`: checks for the four pure modules, for online rooms (`room.test.ts`) and for how an online round feels over slow, uneven connections (`predict.test.ts`) (most build their arenas with `roundTicks: 0`, so the timer does not get in the way of what they check). `experiments/`: control-tuning simulations and CPU player matches, not part of the game.
- `docs/`: read `docs/CODE-GUIDE.md` first. `docs/ROADMAP.md` has the plan and every decision so far.

## Rules that must hold

1. `sim.ts`, `swipe.ts`, `teach.ts`, `bot.ts` and `net.ts` stay pure: no DOM, no `Math.random`, no clocks. The same seed and inputs must always give the same match, CPU players included (tests check it). Online play depends on it: the server runs `sim.ts` and `bot.ts`, and every page steps its own copy of the world with the server's inputs. Keep transcendental maths (`Math.sin`, `Math.atan2`...) out of `sim.ts` and `bot.ts`: engines may round them differently.
2. Rendering only reads the world. The rules never draw or play sound; they report events.
3. Game numbers are named constants at the top of `sim.ts`; pad numbers at the top of `swipe.ts`; CPU level settings in the `LEVELS` table at the top of `bot.ts`.
4. No image or sound files, and no new runtime dependencies. The build stays one self-contained HTML file.
5. Every screen works on an upright phone about 390 px wide, and sideways.
6. All art, code and sound are original. Do not copy from Bomberman or from `TommyBez/bomberman` (the project that inspired this one has no licence; it was used for ideas only).

Things drawn round it use `ROBOT` (head, top, shoulders, and `scale` for the size of the wings and halo), not numbers of their own; a carried bomb sits just over the helmet (`ROBOT.top`).
- Every canvas is drawn at the phone's own pixel density (`density()` in `main.ts`, capped at 6 by `MAX_DENSITY` only to bound sprite memory) and re-laid out whenever the density or size changes (`keepSharp`, every frame). A cap of 3, then of 4, made the arena blurry on the owner's phone, whose zoomed page reports more: do not lower it. Settings › Graphics › Sharpness says what the screen reports and what the game draws at, to tell such a case apart. The arena is sized and placed in whole page pixels on a whole-density screen (`wholeTile` in setup.ts picks the tile size; `onPixel` in `layout`): at density 3 a third of a page pixel is not one of Safari's 64ths, and an arena sized in thirds was stretched by a hair and smoothed all over (the blur that came back in November 2026; computers at density 2 never show it, so check `wholeTile`'s test, not a screenshot). Pinch and double-tap zoom are blocked during play. The arena is placed on a whole screen pixel, and the lobby's arena picture is sized to exactly what it draws, redrawn when its room changes (it was stretched a little, and drawn at a guessed size while its page was hidden).
- Robots are drawn from sprites (`sprite`, `drawRobot`, `warmRobots` in `robot.ts`; `warmSprites` in `render.ts`, called every frame from `main.ts`). Never draw a robot piece by piece every frame. A new pose that changes the picture needs to be part of the sprite's key; one that only moves, turns or scales it (`jump`, `lean`, `shrink`, the crown) does not.
- The soft rounding inside each piece (`FINE`, `softly`) is only for artwork over 500 pixels tall. It blurs with a canvas shadow because iPhones lack the canvas blur filter, and has only been tried in Chrome: try it on an iPhone before using it on a screen of the game.
- Bricks and solid blocks fill their tile. Power-ups are a square of pulsing colour 83% of a tile across (`ITEM_SIZE` in `render.ts`; made 10% smaller than the first size), bobbing slowly over a shadow (`ITEM_BOB`, `ITEM_BOB_RATE`).
- Up to eight players (`MAX_PLAYERS` in `sim.ts`; the owner's limit, after a first version allowed nine): you and one to seven CPU players. Where they start is `spawnPoints` (the owner's plan): four in the corners; a fifth in the middle; six put two in the middle row a third of the way in; seven add the middle of the top and bottom edges to five; eight use the corners and the middle of each edge. With more than six players the arena is two tiles bigger each way (`GROW_AFTER`, `arenaSize` in `setup.ts`). With more than four, the scoreboard has one place per player: upright in the free line under the top bar (the line kept for information), sideways in rows of five under the timer, with the swipe pad starting under them (`--pad-top`).
- The other bots are CPU players (`src/bot.ts`, explained in `docs/CPU-PLAYERS.md`): one to seven, as the lobby says. Nine Hard CPU players took under half a millisecond a tick on a laptop (measured when nine were allowed). Three levels: Beginner, Normal (default) and Hard, set for each CPU player on its own in the lobby (or all at once with All CPUs). A saved `cpuLevel` from before the lobby becomes every CPU player's level.
- CPU players get a `PlayerInput` like a person and nothing more: no extra speed, no seeing under bricks.
- CPU players want a shield, never go looking for a curse, and Normal and above walk round one when there is another way (`dodgeCurse`). They know where blocks will fall, each level looking a different distance ahead (`blockSight`), and move inward ahead of them; they keep fighting while they do. Once the timer has run out and they are standing in the square, Normal and Hard press (`squareBold`, `emboldened` in `bot.ts`): they bomb any player in line, use every bomb, drop bombs beside players to take their room away, and stop holding back in case a rival shuts their way out. Beginner does not. They do not take risks because they hold a shield. Once a shield has taken a blast they use the half second to walk out through it (`sparedFor`).
- No level is careless with its own bombs. Before pressing A every level needs a way out, no watched player able to shut it (`guard`), and the move played forward on a copy of the world (`placeBomb`). Easy levels are easy by being slow and unambitious. There were four levels at first; Extreme was renamed Hard, the old Hard was dropped, and Normal was eased a little (`think` 16, `hesitate` 6 to 26, `notice` 22, `hunt` 0.55, `attack` 0.5). A saved `cpuLevel` of `extreme` is read as `hard`. Beginner was eased once already after play-testing (`hesitate` 40 to 110, `notice` 70, `hunt` 0.12, `attack` 0.2); if it is still too hard, those four and `think` are the ones to turn further.

- Online play (built November 2026; `docs/ONLINE.md`): rooms by four-letter code, made from Title › Online; a link with `?room=CODE` opens the join panel; the lobby's share button sends that link. The lobby is the same lobby, with the other people in the room as player cards (`Guest.remote`; P1 the room's maker, then people in joining order, then CPU players). Each person picks their robot and presses Ready on their own screen. The host (whoever made the room) sets the CPU players and the rules; the others see the Match page read-only (`inert`). Only the host starts, and is asked first if someone is not ready. A room needs someone to play against, a CPU player or a person. The round cannot be paused: the menu opens and the round goes on behind it (the owner's choice). Only the host has Restart (the whole match, for everyone) and End match (everyone back to the lobby), and Next round, Rematch and Lobby at the end of a round; the others see who starts it. Everyone has Leave the room. Online, rounds are played out (no random winner when you are out). A dropped connection keeps its place and comes back into the round; a reload goes straight back in; a host gone 12 s hands the room on. The server runs the round and sends every page each tick's inputs; pages step their own copy of its world, with a checksum every half second (`worldHash`). What is drawn is a picture run ahead of that world (`predict.ts`; built after the owner found the first version laggy and jerky, and asked for it to be smooth): your robot moves the frame you press, presses say which tick they are for and the server keeps them until then, the page's clock runs ahead by the trip there and back (pings twice a second), and the other robots are drawn where the server last said, a few ticks back, never guessed at. Scores and results come only from the server's world. The menu shows the ping. Do not go back to drawing the server's world as it arrives, or to holding ticks back to step them evenly: that was the lag and the stutter. Your own setup and robot on this screen are kept aside while in a room and come back when you leave. Couch play is for this screen only, not online.

## Working on controls and feel

You cannot feel touch controls. Say so, and do not claim a feel problem is fixed until it has been played on a phone.

- Find a concrete cause before changing numbers. Reproduce it in a test or an experiment script (`experiments/` shows how: replay a made-up thumb path through the real code and count what happens).
- Change one thing at a time and say what should feel different.
- When a report is "it goes the wrong way", check both halves: how the pad read the swipe (`swipe.ts`) and what the robot did with that direction (`movePlayer` in `sim.ts`).

## Working on CPU players

- A feel report ("too easy", "it never comes for me") is a change to one level's line in `LEVELS`. Change one setting at a time and say what should be different.
- After any change to `bot.ts`, or to a rule the CPU players depend on: `npm test`, then `npx tsx experiments/cpu-matches.ts` (about fifteen minutes) and the same with `solo`, `versus` and `alone`. "Blasted itself" must stay at zero. Update the tables in `docs/CPU-PLAYERS.md` and `experiments/README.md`.
- Known gap: a CPU player with no safe route left stands still (`doing = 'trapped'` in `flee`). A last-ditch run is not built; a negative margin in `explore` is not the fix on its own, because it would also run them into flames they could have waited out.
- "Blasted itself" and "shut in by a rival" are told apart by `shutIn` in `experiments/cpu-matches.ts` (and by `cause` in `playMatch`, for a bot's bomb set off early by a rival's bomb that was dropped, kicked or thrown afterwards). If a run shows anything under "blasted itself", replay it (seed and corner order are in the script) before changing the bot or the test.
- Be suspicious of numbers that look too good. A level that never blasts itself may be a level that never drops a bomb: check it also gets the still target in the `solo` run.
- You cannot tell how hard a level is for a person. Say so; it has to be played.
