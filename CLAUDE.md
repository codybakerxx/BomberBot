# BomberBot: notes for Claude

BomberBot is a top-down bomber battle game for the browser, built for phones. The owner directs the project and play-tests every change on a phone. Claude writes the code. Explain what you did in plain words, and lead with what changed for the player.

## Commands

```sh
npm install        # once
npm run check      # type-check, tests, build: run this before calling anything done
npm test           # tests only
npm run build      # writes dist/index.html, the whole game in one file
```

## Where things are

- `src/sim.ts`: all game rules. `src/swipe.ts`: the swipe pad and Movement sensitivity. `src/bot.ts`: the CPU players.
- `src/input.ts`, `src/render.ts`, `src/audio.ts`: input wiring, drawing, sound. `src/quick.ts`: the quick chat, its bubbles under the heads on the scoreboard, and the quick menu (the menu button held). `src/robot.ts`: how the robot is drawn (handed on through `render.ts`). `src/railway.ts`: the Wild West's railway, train and TNT, drawn (called from `render.ts`). `src/factory.ts`: the Factory's floor, machines, boxes, belts, beacons and furnaces, drawn (called from `render.ts`).
- `src/main.ts`: loop, title screen, Settings, the menu during a match, the score, layout. `src/lobby.ts`: the lobby. `src/setup.ts`: what the lobby and Settings choose, and saving it. `src/ui.ts`: the menus' controls. `src/title.ts`: the title screen's picture. `src/page.html`: markup and styles.
- Online play (`docs/ONLINE.md`): `src/net.ts` (the messages, input codes, checksums: pure), `src/room.ts` (one room: lobby, host, the match, run on the server; no network or clock of its own), `src/worker.ts` (the Cloudflare server: a Durable Object per room code), `src/online.ts` (the page's connection), `src/predict.ts` (the round on the page: the picture run ahead of the server so your robot moves at once; pure, the time is handed in). `wrangler.jsonc` says what is uploaded; GitHub uploads it on every push to `main`. The game is at https://bomberbot.bomberbot.workers.dev.
- Website and app (Settings › App): `src/app.ts` (home screen, notifications on the page), `src/push.ts` (signing and locking a notification), `Friends` in `src/worker.ts` (who gets them), `src/sw.js` (works offline, shows notifications). The icon: `drawIcon` in `src/title.ts`.
- `tests/`: checks for the pure modules, for online rooms (`room.test.ts`) and for how an online round feels over slow, uneven connections (`predict.test.ts`) (most build their arenas with `roundTicks: 0`, so the timer does not get in the way of what they check). `experiments/`: control-tuning simulations and CPU player matches, not part of the game.
- `docs/`: read `docs/CODE-GUIDE.md` first. `docs/ROADMAP.md` has the plan and every decision so far.

## Rules that must hold

1. `sim.ts`, `swipe.ts`, `bot.ts` and `net.ts` stay pure: no DOM, no `Math.random`, no clocks. The same seed and inputs must always give the same match, CPU players included (tests check it). Online play depends on it: the server runs `sim.ts` and `bot.ts`, and every page steps its own copy of the world with the server's inputs. Keep transcendental maths (`Math.sin`, `Math.atan2`...) out of `sim.ts` and `bot.ts`: engines may round them differently.
2. Rendering only reads the world. The rules never draw or play sound; they report events.
3. Game numbers are named constants at the top of `sim.ts`; pad numbers at the top of `swipe.ts`; CPU level settings in the `LEVELS` table at the top of `bot.ts`.
4. No image or sound files, and no new runtime dependencies. The game stays one self-contained HTML file. Beside it on the website, only what a phone needs to treat it as an app: the home-screen icons (`public/icon-*.png`, drawn by the game's own code with `tools/icons.py`), the manifest and the service worker (`src/sw.js`), written by `build.mjs`. The page plays without them (opened as a file).
5. Every screen works on an upright phone about 390 px wide, and sideways.
6. All art, code and sound are original. Do not copy from Bomberman or from `TommyBez/bomberman` (the project that inspired this one has no licence; it was used for ideas only).

## Working on controls and feel

You cannot feel touch controls. Say so, and do not claim a feel problem is fixed until it has been played on a phone.

- Find a concrete cause before changing numbers. Reproduce it in a test or an experiment script (`experiments/` shows how: replay a made-up thumb path through the real code and count what happens).
- Change one thing at a time and say what should feel different.
- When a report is "it goes the wrong way", check both halves: how the pad read the swipe (`swipe.ts`) and what the robot did with that direction (`movePlayer` in `sim.ts`).

## Before finishing

- `npm run check` passes.
- A rule or number changed: add or update a check in `tests/`, and update the tables in `docs/GAME-RULES.md`, `docs/CONTROLS.md`, `docs/SWIPE-HISTORY.md` or `docs/CPU-PLAYERS.md`.
- The screen changed: retake screenshots with `tools/screenshots.py` if Python and Chrome are available, and run `tools/layout-check.py`: it walks every screen at eight phone sizes (320 to 440 wide, and sideways) with the longest names and most players, and lists text out of its box, things sticking out of their cards, anything off the screen, a chip running under a button. That kind of fault got through four times in one day before it existed. A screen seen online (the lobby's top bar, the bell, the menu during a match): run it with `npx wrangler dev` going and `URL=http://127.0.0.1:8787/`, which hosts a room at every size too.
- Anything that draws or lays out the arena changed: run `tools/sharp-check.py`. A canvas added, moved or made `position: fixed`, or the page's start-up changed: `npm test` (`tests/page.test.ts`) and, where WebKitGTK can be installed, `tools/webkit-check.py` (its docstring says how).
- A decision was made: add it to `docs/ROADMAP.md` and to the list above.

## Working on online play

- You cannot feel a connection either. Measure: `npm run build`, `npx wrangler dev`, then `tools/online-feel.py` at 5,2, 35,25 and 70,50, before and after. Press-to-move should stay at about one frame (20 to 27 ms in the test) and "uneven" in single figures, as playing on one screen measures. `docs/ONLINE.md` has the table.
- `tests/predict.test.ts` checks the same without a browser. If a change makes it fail, the change is wrong, not the limits.
- The real path from a phone to Cloudflare cannot be reached from Claude's sessions. If the owner reports lag again, ask for the ping shown in the menu during an online match before changing anything.
- The server (`room.ts`) and the page (`predict.ts`) must take presses in the same way: both use `takeInput` in `net.ts`. Change it there or not at all.

## Working on CPU players

- A feel report ("too easy", "it never comes for me") is a change to one level's line in `LEVELS`. Change one setting at a time and say what should be different.
- After any change to `bot.ts`, or to a rule the CPU players depend on: `npm test`, then `npx tsx experiments/cpu-matches.ts` (about fifteen minutes) and the same with `solo`, `versus`, `alone` and `duel`. "Blasted itself" must stay at zero. Update the tables in `docs/CPU-PLAYERS.md` and `experiments/README.md`.
- After a change to the belts or to how CPU players handle them: the same runs with `BELTS=1` in front. Midnight, the Wild West and Frozen Lake must play exactly as before: every belt change is gated on `world.belts.length`.
- Known gap: a CPU player with no safe route left stands still (`doing = 'trapped'` in `flee`). Before that, since 26 November 2026, it takes a way to somewhere clear of every blast due in the next second (`breathing`, `BREATHE` 60 ticks) and thinks again from there; and on Frozen Lake only, it then plays standing still and the nearest ways out forward on a copy of the world (`lastDitch`), since there the danger map sees least well; on the other maps a last-ditch run is not built. A negative margin in `explore` is not the fix on its own, because it would also run them into flames they could have waited out.
- "Blasted itself" and "shut in by a rival" are told apart by `shutIn` in `experiments/cpu-matches.ts` (and by `cause` in `playMatch`, for a bot's bomb set off early by a rival's bomb that was dropped, kicked or thrown afterwards). If a run shows anything under "blasted itself", replay it (seed and corner order are in the script) before changing the bot or the test.
- Be suspicious of numbers that look too good. A level that never blasts itself may be a level that never drops a bomb: check it also gets the still target in the `solo` run.
- You cannot tell how hard a level is for a person. Say so; it has to be played.
